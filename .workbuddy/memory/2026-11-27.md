## testmiku 映射异常诊断（用户截图）

现象：已填 52/64，但「下半身 0.75」「左足 0.91」「右ひざ 0.91」等高分字段留空，且「センター」填成了 Hips。

**根因（已复现）**：
1. `_solve_backtrack` 原按「候选数少优先」排序。`center_bone` 在 3ds_max/bepu/motion_builder 预设里就是 Hips（名称 0.40 满分），且候选仅 2 个；`lower_body_bone` 有 7 个候选。于是中心骨先拿走 Hips，腰/下半身无骨可用。
2. 链约束 `lower_body_bone → left_thigh_bone → left_calf_bone → ...` 连锁失效，高分腿骨字段跟着留空。
3. 搜索节点上限 200000 在 11 根骨的简化骨架上就打满，DFS 被截断后退化为错误贪心；真实 93 根骨更严重。

**修复**：
- 排序改为「最高候选分优先，候选数次之」。简化骨架复验：填充 6→11，主链全部正确（下半身=Hips、上半身=Spine、左足=UpperLeg_L）。
- 新增 `explain_missing()`，提示具体占用者，如「候选 Hips 已被 下半身 占用」。
- 14 项单测通过，语法检查通过。
- 关键认知：此问题的本质不是阈值，而是**字段抢占顺序 + 搜索截断**。用户给的「规模很小所以贪心+回溯」假设在 64 字段×6 候选下不成立。

### 追加：Chest/Spine 存在但「胸親父级」留空

  2. 0.54 低于 `CONFIDENCE_THRESHOLD=0.55`，差 0.01。

### UI：骨骼名称列固定宽度（尝试后撤销）

- 关键认知：Blender `UILayout` **没有固定像素宽度 API**。`split(factor)` 是比例，窄面板必然压缩；补空格靠 label 自然宽度撑开时，同行 `prop_search` 弹性控件会挤占空间，尾部空格不产生稳定占位。纯 UI API 无法可靠固定列宽，除非改用两行布局（名称单独一行）或自定义绘制。

### 右胸误选 Chest 候选（用户截图反馈）

- 现象：面板提示「右胸 0.56（候选 Chest 已被 上半身2 占用）」。
- 根因：`ALIAS_TOKENS` 里 `left/right_chest_bone` 都含 `("chest",)`，中轴 `Chest` 以名称包含匹配 0.25 进候选；左右符号本版是软打分（中轴得 0 但不淘汰），总分 0.56。同一根骨 `upper_body2_bone` 是精确匹配 0.40、总分 0.75，先抢走 → 右胸留空。
